# LLM 인기도 웹사이트 PRD (Product Requirements Document)

## 1. Executive Summary (요약)

### 1.1 프로덕트 개요
LLM(Large Language Model)의 종류와 인기도를 시각화하고 비교할 수 있는 웹 애플리케이션입니다. 개발자들이 다양한 LLM을 탐색하고, 인기도 지표를 비교하며, 프로젝트에 적합한 LLM을 선택할 수 있도록 돕는 정보 플랫폼입니다.

### 1.2 핵심 가치 제안
- **중앙화된 LLM 정보**: 다양한 LLM의 정보를 한 곳에서 확인
- **데이터 기반 의사결정**: 객관적인 인기도 지표를 통한 LLM 선택 지원
- **비교 분석**: 여러 LLM을 동시에 비교하여 최적의 선택 도움
- **실시간 업데이트**: API를 통한 최신 데이터 제공

### 1.3 목표
- 개발자들이 LLM 선택 시 소요 시간 50% 단축
- 월간 활성 사용자 10,000명 달성 (6개월 내)
- 사용자 만족도 4.5/5.0 이상

### 1.4 주요 특징
- LLM 목록 및 상세 정보 제공
- 다차원 인기도 지표 (GitHub Stars, 다운로드 수, 논문 인용 수 등)
- LLM 비교 기능
- 고급 필터링 및 검색 기능
- Flutter 웹 기반 반응형 디자인

## 2. Problem Statement (문제 정의)

### 2.1 해결하려는 문제
현재 개발자들은 LLM을 선택할 때 다음과 같은 어려움을 겪고 있습니다:

1. **정보 분산**: LLM 정보가 여러 플랫폼(GitHub, 논문 사이트, 블로그 등)에 분산되어 있음
2. **주관적 평가**: 객관적인 데이터 없이 주관적인 리뷰에 의존
3. **비교의 어려움**: 여러 LLM을 동시에 비교하기 어려움
4. **최신 정보 부족**: LLM 생태계가 빠르게 변화하는데 최신 정보를 얻기 어려움
5. **인기도 측정의 복잡성**: 다양한 지표(GitHub stars, 다운로드 수 등)를 종합적으로 파악하기 어려움

### 2.2 타겟 사용자의 페인 포인트
- **시간 소모**: 여러 소스를 방문하며 정보를 수집하는데 시간이 많이 소요됨
- **불확실성**: 어떤 LLM이 실제로 인기 있고 신뢰할 수 있는지 판단하기 어려움
- **비교 어려움**: 여러 LLM의 특징과 성능을 한눈에 비교하기 어려움
- **정보 부족**: 특정 LLM의 상세 정보나 최신 업데이트를 찾기 어려움

### 2.3 현재 시장의 한계점
- LLM 비교 사이트들이 제한적이거나 정보가 불완전함
- 대부분의 사이트가 단일 지표에만 집중
- 실시간 업데이트가 되지 않음
- 개발자 친화적인 인터페이스 부족

## 3. Solution Overview (솔루션 개요)

### 3.1 핵심 솔루션
통합된 웹 플랫폼을 통해 개발자들이 LLM 정보를 쉽게 탐색하고 비교할 수 있도록 합니다. API를 통해 다양한 소스에서 데이터를 수집하고, 직관적인 UI로 정보를 시각화합니다.

### 3.2 주요 기능
1. **LLM 목록 표시**: 카드/리스트 형태로 LLM 정보 표시
2. **인기도 지표 통합**: GitHub Stars, 다운로드 수, 논문 인용 수 등 종합 지표
3. **비교 기능**: 최대 3-5개 LLM을 선택하여 상세 비교
4. **필터/검색**: 다양한 조건으로 LLM 필터링 및 검색

### 3.3 차별화 포인트
- **다차원 지표**: 단일 지표가 아닌 종합적인 인기도 평가
- **실시간 데이터**: API를 통한 최신 정보 제공
- **개발자 중심 UX**: 개발자들이 빠르게 정보를 찾을 수 있는 인터페이스
- **Flutter 웹**: 크로스 플랫폼 호환성과 성능

## 4. Target Users (타겟 사용자)

### 4.1 사용자 페르소나

#### 페르소나 1: 주니어 개발자 "김개발"
- **나이**: 25-30세
- **역할**: 풀스택 개발자
- **경험**: LLM을 프로젝트에 처음 도입하려는 개발자
- **목표**: 프로젝트에 적합한 LLM을 빠르게 찾고 싶음
- **페인 포인트**: 어떤 LLM이 좋은지 모르고, 정보를 찾기 어려움
- **사용 시나리오**: 
  - 챗봇 프로젝트를 시작하며 적합한 LLM 탐색
  - GitHub stars와 커뮤니티 활동을 확인하여 안정적인 LLM 선택

#### 페르소나 2: 시니어 개발자 "박아키텍트"
- **나이**: 30-40세
- **역할**: 기술 리더/아키텍트
- **경험**: 여러 LLM을 평가하고 비교해야 하는 상황
- **목표**: 여러 LLM을 객관적으로 비교하여 최적의 선택
- **페인 포인트**: 여러 소스를 방문하며 비교하는데 시간이 많이 걸림
- **사용 시나리오**:
  - 여러 LLM을 동시에 비교하여 성능과 인기도 평가
  - 팀에 추천할 LLM을 데이터 기반으로 선택

#### 페르소나 3: 연구자 "이연구"
- **나이**: 25-35세
- **역할**: AI/ML 연구자
- **경험**: 최신 LLM 트렌드를 파악하고 싶은 연구자
- **목표**: 최신 LLM과 논문 인용 수를 확인
- **페인 포인트**: 논문 인용 수와 실제 사용량의 관계를 파악하기 어려움
- **사용 시나리오**:
  - 최신 LLM 논문과 실제 인기도를 함께 확인
  - 연구 방향 결정을 위한 LLM 트렌드 파악

### 4.2 사용자 여정 (User Journey)

#### 여정 1: LLM 탐색
1. **인지**: "프로젝트에 LLM이 필요한데 어떤 걸 써야 하지?"
2. **방문**: 웹사이트 접속
3. **탐색**: LLM 목록을 스크롤하며 둘러봄
4. **필터링**: 용도(챗봇, 코드 생성 등)로 필터링
5. **상세 확인**: 관심 있는 LLM의 상세 정보 확인
6. **의사결정**: 인기도와 특징을 보고 선택

#### 여정 2: LLM 비교
1. **인지**: "여러 LLM 중에서 선택해야 해"
2. **방문**: 웹사이트 접속
3. **검색**: 비교하고 싶은 LLM 검색
4. **선택**: 여러 LLM 선택하여 비교 모드 진입
5. **비교**: 지표와 특징을 나란히 비교
6. **의사결정**: 비교 결과를 바탕으로 최종 선택

### 4.3 사용 사례 (Use Cases)

#### Use Case 1: 프로젝트에 적합한 LLM 찾기
- **액터**: 개발자
- **전제 조건**: 프로젝트 요구사항이 있음
- **주 흐름**:
  1. 웹사이트 접속
  2. 필터에서 프로젝트 요구사항 선택 (예: 오픈소스, 상업적 사용 가능)
  3. 결과 목록에서 인기도 순으로 정렬
  4. 상위 LLM들의 상세 정보 확인
  5. 적합한 LLM 선택
- **대안 흐름**: 검색어로 직접 검색

#### Use Case 2: 여러 LLM 비교
- **액터**: 기술 리더
- **전제 조건**: 후보 LLM 목록이 있음
- **주 흐름**:
  1. 웹사이트 접속
  2. 비교하고 싶은 LLM 검색
  3. 각 LLM을 비교 목록에 추가 (최대 5개)
  4. 비교 페이지에서 지표와 특징 비교
  5. 비교 결과를 바탕으로 의사결정
- **대안 흐름**: 비교 목록에서 LLM 제거 후 다른 LLM 추가

#### Use Case 3: 최신 LLM 트렌드 파악
- **액터**: 연구자/개발자
- **전제 조건**: 최신 정보에 관심이 있음
- **주 흐름**:
  1. 웹사이트 접속
  2. "최신 추가" 또는 "인기 급상승" 필터 선택
  3. 최신 LLM 목록 확인
  4. 각 LLM의 인기도 지표 확인
  5. 트렌드 파악

## 5. Features & Requirements (기능 및 요구사항)

### 5.1 Feature 1: LLM 목록 표시

#### 5.1.1 기능 설명
메인 페이지에서 LLM 목록을 카드 또는 리스트 형태로 표시합니다. 각 LLM 카드에는 기본 정보와 주요 인기도 지표가 표시됩니다.

#### 5.1.2 우선순위
**Must Have**

#### 5.1.3 기능적 요구사항

**FR-1.1: LLM 카드 표시**
- 각 LLM은 카드 형태로 표시되어야 함
- 카드에는 다음 정보가 포함되어야 함:
  - LLM 이름
  - 개발자/조직명
  - 짧은 설명 (최대 100자)
  - 주요 인기도 지표 (GitHub Stars, 다운로드 수 등)
  - LLM 타입 (예: 오픈소스, 상업용)
  - 썸네일 이미지 또는 로고
- 카드 클릭 시 상세 페이지로 이동

**FR-1.2: 목록 정렬**
- 다음 기준으로 정렬 가능해야 함:
  - 인기도 순 (기본값)
  - GitHub Stars 순
  - 최신 추가 순
  - 이름 순 (알파벳/한글)
- 정렬 옵션은 드롭다운 또는 버튼으로 제공

**FR-1.3: 페이지네이션**
- 한 페이지에 20개의 LLM 표시
- 무한 스크롤 또는 페이지 번호 방식 지원
- 총 LLM 수 표시

**FR-1.4: 로딩 상태**
- 데이터 로딩 중 로딩 인디케이터 표시
- 스켈레톤 UI로 로딩 상태 표현

**FR-1.5: 에러 처리**
- API 오류 시 사용자 친화적인 에러 메시지 표시
- 재시도 버튼 제공

#### 5.1.4 비기능적 요구사항

**NFR-1.1: 성능**
- 초기 로딩 시간: 2초 이내
- 카드 렌더링: 60fps 유지
- API 응답 시간: 1초 이내

**NFR-1.2: 반응형 디자인**
- 데스크톱: 3-4열 그리드
- 태블릿: 2열 그리드
- 모바일: 1열 그리드

**NFR-1.3: 접근성**
- WCAG 2.1 AA 수준 준수
- 키보드 네비게이션 지원
- 스크린 리더 호환

#### 5.1.5 사용자 스토리
```
As a 개발자,
I want to LLM 목록을 한눈에 볼 수 있도록,
So that 빠르게 관심 있는 LLM을 찾을 수 있다.
```

#### 5.1.6 수용 기준
- [ ] LLM 목록이 카드 형태로 표시됨
- [ ] 각 카드에 필수 정보가 모두 표시됨
- [ ] 정렬 기능이 정상 작동함
- [ ] 페이지네이션이 정상 작동함
- [ ] 반응형 디자인이 모든 화면 크기에서 작동함
- [ ] 로딩 및 에러 상태가 적절히 처리됨

### 5.2 Feature 2: 인기도/사용량 지표

#### 5.2.1 기능 설명
각 LLM의 인기도를 다양한 지표로 측정하고 시각화합니다. GitHub Stars, 다운로드 수, 논문 인용 수 등을 통합하여 종합 인기도 점수를 계산합니다.

#### 5.2.2 우선순위
**Must Have**

#### 5.2.3 기능적 요구사항

**FR-2.1: 지표 수집**
- 다음 지표를 수집해야 함:
  - GitHub Stars 수
  - GitHub Forks 수
  - PyPI/Hugging Face 다운로드 수
  - 논문 인용 수 (Google Scholar, Semantic Scholar)
  - 최근 커밋 활동
  - 이슈/PR 활동
- 지표는 API를 통해 주기적으로 업데이트

**FR-2.2: 종합 인기도 점수**
- 각 지표를 가중치를 적용하여 종합 점수 계산
- 점수는 0-100 스케일로 표시
- 점수 계산 공식:
  ```
  종합 점수 = (GitHub Stars 정규화 * 0.3) + 
              (다운로드 수 정규화 * 0.3) + 
              (논문 인용 수 정규화 * 0.2) + 
              (커뮤니티 활동 정규화 * 0.2)
  ```

**FR-2.3: 지표 시각화**
- 각 지표를 숫자와 함께 진행 바 또는 차트로 표시
- 지표별 트렌드 그래프 제공 (최근 6개월)
- 지표 비교를 위한 레이더 차트 제공

**FR-2.4: 지표 상세 정보**
- 각 지표 클릭 시 상세 정보 모달 표시
- 지표 출처 및 마지막 업데이트 시간 표시
- 지표 설명 툴팁 제공

#### 5.2.4 비기능적 요구사항

**NFR-2.1: 데이터 정확성**
- 지표 데이터는 최소 일 1회 업데이트
- 데이터 불일치 시 경고 표시

**NFR-2.2: 성능**
- 지표 계산은 서버 사이드에서 수행
- 클라이언트는 계산된 점수만 수신

#### 5.2.5 사용자 스토리
```
As a 개발자,
I want to LLM의 객관적인 인기도 지표를 확인하고,
So that 신뢰할 수 있는 LLM을 선택할 수 있다.
```

#### 5.2.6 수용 기준
- [ ] 모든 필수 지표가 수집되고 표시됨
- [ ] 종합 인기도 점수가 정확하게 계산됨
- [ ] 지표가 시각적으로 잘 표현됨
- [ ] 지표 데이터가 정기적으로 업데이트됨
- [ ] 지표 상세 정보를 확인할 수 있음

### 5.3 Feature 3: 비교 기능

#### 5.3.1 기능 설명
사용자가 최대 5개의 LLM을 선택하여 나란히 비교할 수 있는 기능입니다. 지표, 특징, 성능 등을 테이블 형태로 비교합니다.

#### 5.3.2 우선순위
**Must Have**

#### 5.3.3 기능적 요구사항

**FR-3.1: LLM 선택**
- LLM 목록에서 "비교에 추가" 버튼 클릭
- 비교 목록에 최대 5개까지 추가 가능
- 비교 목록은 상단에 고정된 바로 표시
- 비교 목록에서 LLM 제거 가능

**FR-3.2: 비교 테이블**
- 선택된 LLM들을 테이블 형태로 나란히 표시
- 비교 항목:
  - 기본 정보 (이름, 개발자, 설명)
  - 인기도 지표 (종합 점수, GitHub Stars, 다운로드 수 등)
  - 기술 사양 (모델 크기, 파라미터 수, 컨텍스트 길이)

### 7.4 API 설계

#### 7.4.1 엔드포인트

**LLM 목록**
- `GET /api/v1/llms`
  - Query params: `page`, `limit`, `sort`, `filter`
  - Response: `{ data: LLM[], total: number, page: number }`

**LLM 상세**
- `GET /api/v1/llms/:id`
  - Response: `{ data: LLM }`

**LLM 검색**
- `GET /api/v1/llms/search?q=:query`
  - Response: `{ data: LLM[] }`

**LLM 비교**
- `POST /api/v1/llms/compare`
  - Body: `{ ids: string[] }`
  - Response: `{ data: LLM[] }`

**인기도 지표**
- `GET /api/v1/llms/:id/metrics`
  - Response: `{ data: PopularityMetrics }`

## 12. Risks & Mitigation (리스크 및 완화 방안)

### 12.1 기술적 리스크

#### 리스크 1: API 제한 및 비용
**설명**: GitHub API, Hugging Face API 등의 rate limit 및 비용 문제

**영향**: 높음  
**확률**: 중간

**완화 방안:**
- API 키를 여러 개 준비하여 로테이션
- 캐싱을 적극 활용하여 API 호출 최소화
- 무료 티어 내에서 운영 가능한 구조 설계
- 필요 시 유료 플랜 검토

#### 리스크 2: 데이터 수집의 어려움
**설명**: 일부 LLM의 정보가 공개되지 않거나 수집하기 어려움

**영향**: 중간  
**확률**: 높음

**완화 방안:**
- 수동 데이터 입력 시스템 구축
- 커뮤니티 기여 기능 추가
- 데이터가 없는 경우 명시적으로 표시
- 점진적으로 데이터 확장

#### 리스크 3: Flutter Web 성능
**설명**: Flutter Web의 번들 크기 및 성능 이슈

**영향**: 중간  
**확률**: 낮음

**완화 방안:**
- 코드 스플리팅 적용
- 이미지 최적화 및 lazy loading
- 성능 프로파일링 및 최적화
- 필요 시 일부 기능을 네이티브 웹으로 구현

### 12.2 비즈니스 리스크

#### 리스크 4: 사용자 확보 실패
**설명**: 목표 사용자 수에 도달하지 못함

**영향**: 높음  
**확률**: 중간

**완화 방안:**
- SEO 최적화
- 개발자 커뮤니티에 홍보 (Reddit, Hacker News, Dev.to)
- GitHub에 오픈소스로 공개
- 콘텐츠 마케팅 (블로그, 튜토리얼)

#### 리스크 5: 데이터 정확성 문제
**설명**: 잘못된 데이터로 인한 신뢰도 하락

**영향**: 높음  
**확률**: 낮음

**완화 방안:**
- 데이터 검증 로직 구현
- 정기적인 데이터 품질 검사
- 사용자 피드백 시스템 구축
- 데이터 출처 명시

### 12.3 운영 리스크

#### 리스크 6: 서버 비용 증가
**설명**: 사용자 증가에 따른 인프라 비용 증가

**영향**: 중간  
**확률**: 중간

**완화 방안:**
- 효율적인 캐싱 전략
- CDN 활용
- 서버리스 아키텍처 고려
- 모니터링을 통한 비용 최적화
