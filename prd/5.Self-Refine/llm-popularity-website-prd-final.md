# LLM 인기도 웹사이트 PRD (최종 버전)

## 1. 프로젝트 개요

### 1.1 목적
AI 분야에서 사용되는 다양한 LLM(Large Language Model)의 종류와 **다각도 인기도 지표**를 시각적으로 보여주는 웹사이트를 개발한다.

### 1.2 배경
최근 AI 기술이 급속히 발전하면서 다양한 LLM이 출시되고 있다. 개발자와 연구자들이 어떤 LLM이 어떤 관점에서 인기 있는지, 어떤 특징을 가지고 있는지 쉽게 파악할 수 있는 플랫폼이 필요하다.

### 1.3 타겟 사용자
- **주 타겟**: AI/ML 개발자 및 엔지니어
  - 프로젝트에 적합한 LLM을 선택하려는 개발자
  - 최신 트렌드를 파악하려는 개발자
- **부 타겟**: AI 연구자 및 학생
  - 학술적 영향력을 파악하려는 연구자
  - 학습 목적으로 다양한 LLM을 비교하려는 학생

### 1.4 차별화 포인트
- **다각도 인기도 지표 제공**: 단일 "인기도"가 아닌 여러 관점의 인기도를 분리하여 제공
- **사용자 커스터마이징**: 사용자가 관심 있는 지표에 가중치를 두어 개인화된 인기도 계산
- **실시간 트렌드**: 시간에 따른 인기도 변화를 시각화하여 트렌드 파악 용이

## 2. 핵심 기능

### 2.1 LLM 목록 및 정보 표시
- 주요 LLM들의 목록을 카드 형태로 표시
- 각 LLM의 기본 정보:
  - 제작사/기관
  - 출시일
  - 파라미터 수
  - 라이선스 유형
  - 주요 특징 및 용도
  - 공식 문서 링크

### 2.2 다각도 인기도 지표 (핵심 기능)

#### 2.2.1 인기도 지표 분류 및 정의

**A. 개발자 커뮤니티 인기도 (Developer Community Popularity)**
- **측정 지표:**
  - GitHub Stars 수 (가중치: 40%)
  - GitHub Forks 수 (가중치: 20%)
  - GitHub Issues/PR 활동도 (가중치: 20%)
  - Stack Overflow 태그 사용 빈도 (가중치: 20%)
- **데이터 소스:** GitHub API, Stack Overflow API
- **업데이트 주기:** 일일
- **의미:** 실제 개발자들이 얼마나 관심을 가지고 사용하는지

**B. 학술적 영향력 (Academic Influence)**
- **측정 지표:**
  - 논문 인용 수 (가중치: 60%)
  - 관련 논문 수 (가중치: 20%)
  - 최근 1년 인용 증가율 (가중치: 20%)
- **데이터 소스:** Google Scholar API, Semantic Scholar API
- **업데이트 주기:** 주간
- **의미:** 학술 커뮤니티에서의 영향력

**C. 실용적 채택도 (Practical Adoption)**
- **측정 지표:**
  - Hugging Face 다운로드 수 (가중치: 50%)
  - PyPI/패키지 매니저 다운로드 수 (가중치: 30%)
  - Docker Hub Pulls (가중치: 20%)
- **데이터 소스:** Hugging Face API, PyPI API, Docker Hub API
- **업데이트 주기:** 일일
- **의미:** 실제 프로덕션 환경에서의 사용 빈도

**D. 커뮤니티 활성도 (Community Activity)**
- **측정 지표:**
  - Reddit 관련 게시물 수 (가중치: 30%)
  - Discord/포럼 멤버 수 (가중치: 30%)
  - 최근 30일 활동 증가율 (가중치: 40%)
- **데이터 소스:** Reddit API, 커뮤니티 포럼 데이터
- **업데이트 주기:** 주간
- **의미:** 커뮤니티의 활발한 토론 및 지원

#### 2.2.2 통합 인기도 점수 (선택적)

사용자가 원할 경우, 다음 공식으로 통합 인기도 점수를 계산:

```
통합 인기도 = (개발자 인기도 × W1) + (학술적 영향력 × W2) + 
              (실용적 채택도 × W3) + (커뮤니티 활성도 × W4)

기본 가중치:
- W1 = 0.4 (개발자 인기도)
- W2 = 0.2 (학술적 영향력)
- W3 = 0.3 (실용적 채택도)
- W4 = 0.1 (커뮤니티 활성도)
```

**사용자 커스터마이징:**
- 사용자가 각 카테고리의 가중치를 조정 가능 (슬라이더 UI)
- 프리셋 제공: "개발자 중심", "연구자 중심", "실용 중심" 등

#### 2.2.3 정규화 및 스케일링

모든 지표는 0-100 점수로 정규화:
- 각 지표의 최대값을 100으로 설정
- 최소값을 0으로 설정
- 선형 스케일링 적용

예외 처리:
- 데이터가 없는 경우: 해당 지표는 계산에서 제외하고 가중치를 다른 지표에 재분배
- API 오류 시: 마지막으로 캐시된 데이터 사용

### 2.3 시각화 기능

#### 2.3.1 인기도 대시보드
- 각 LLM별로 4개 카테고리의 인기도를 레이더 차트로 표시
- 시간에 따른 인기도 변화를 라인 차트로 표시 (최근 6개월)
- Top 10 LLM을 바 차트로 표시

#### 2.3.2 트렌드 분석
- 특정 기간 동안 인기도가 가장 빠르게 상승한 LLM (Rising Stars)
- 인기도가 하락하는 LLM (Declining)
- 신규 출시 LLM 강조

### 2.4 비교 기능
- 여러 LLM을 선택하여 나란히 비교
- 비교 항목:
  - 각 인기도 지표 점수
  - 기술적 스펙 (파라미터 수, 컨텍스트 길이 등)
  - 라이선스 정보
  - 비용 정보 (있는 경우)
  - 지원 언어

### 2.5 검색 및 필터링
- LLM 이름으로 검색
- 필터링 옵션:
  - 제작사/기관
  - 라이선스 유형 (오픈소스/상용)
  - 파라미터 수 범위
  - 출시일 범위
- 정렬 옵션:
  - 개발자 인기도순
  - 학술적 영향력순
  - 실용적 채택도순
  - 커뮤니티 활성도순
  - 통합 인기도순 (사용자 설정 가중치 적용)
  - 출시일순
  - 파라미터 수순

## 3. 기술 스택

### 3.1 프론트엔드
- Flutter Web (현재 프로젝트 기반)
- 차트 라이브러리: `fl_chart` 또는 `syncfusion_flutter_charts`
- 상태 관리: Provider 또는 Riverpod

### 3.2 데이터 소스 및 API
- **GitHub API**: Stars, Forks, Issues, PRs
- **Hugging Face API**: 모델 다운로드 통계
- **Google Scholar API / Semantic Scholar API**: 논문 인용 데이터
- **Stack Overflow API**: 태그 사용 통계
- **Reddit API**: 관련 게시물 수
- **PyPI API**: 패키지 다운로드 수

### 3.3 데이터 저장 및 캐싱
- **로컬 캐싱**: SharedPreferences 또는 Hive
  - API 응답을 24시간 캐싱
  - 오프라인 모드 지원
- **백엔드 (선택적)**: 
  - API 호출을 중앙화하여 rate limit 관리
  - 데이터 집계 및 전처리
  - 주기적인 데이터 업데이트 (Cron Job)

### 3.4 데이터 업데이트 전략
- **실시간 데이터**: GitHub, Hugging Face (일일 업데이트)
- **주기적 데이터**: 학술 인용, 커뮤니티 활동 (주간 업데이트)
- **캐싱 전략**: 
  - 첫 방문 시 API 호출
  - 이후 24시간 동안 캐시된 데이터 사용
  - 백그라운드에서 주기적으로 업데이트

## 4. 사용자 경험

### 4.1 메인 페이지

### 4.4 설정 페이지

## 7. 제약사항 및 리스크 관리

### 7.1 기술적 제약사항
- **API Rate Limit**: 
  - 각 API의 무료 티어 제한 내에서 운영
  - 필요시 백엔드 서버를 통해 중앙화하여 관리
  - 캐싱을 통한 API 호출 최소화

- **데이터 가용성**:
  - 모든 LLM이 모든 지표를 가지지 않을 수 있음
  - 데이터가 없는 경우 해당 지표는 "N/A"로 표시하고 계산에서 제외

### 7.2 데이터 품질 관리
- **데이터 검증**: 
  - API 응답의 유효성 검사
  - 이상치 감지 및 필터링
  - 수동 검증을 위한 관리자 대시보드 (선택적)

- **데이터 업데이트 실패 처리**:
  - 실패 시 마지막 성공한 데이터 사용
  - 사용자에게 "데이터 업데이트 중" 표시
  - 재시도 로직 구현

### 7.3 경쟁 서비스 대응
- **차별화 유지**: 다각도 인기도 지표와 커스터마이징 기능 강조
- **지속적인 개선**: 사용자 피드백을 통한 기능 개선
- **데이터 정확성**: 정기적인 데이터 검증 및 업데이트

## 부록: 인기도 계산 예시

### 예시: GPT-4의 인기도 계산

**개발자 커뮤니티 인기도:**
- GitHub Stars: 50,000 (정규화: 85점)
- GitHub Forks: 10,000 (정규화: 80점)
- Issues/PR 활동: 높음 (정규화: 90점)
- Stack Overflow 태그: 5,000회 (정규화: 75점)
- 계산: (85×0.4) + (80×0.2) + (90×0.2) + (75×0.2) = **82.5점**

**학술적 영향력:**
- 논문 인용: 1,000회 (정규화: 95점)
- 관련 논문: 200편 (정규화: 85점)
- 최근 1년 증가율: 300% (정규화: 90점)
- 계산: (95×0.6) + (85×0.2) + (90×0.2) = **92점**

**실용적 채택도:**
- Hugging Face 다운로드: 1,000,000회 (정규화: 100점)
- PyPI 다운로드: 500,000회 (정규화: 90점)
- Docker Pulls: 200,000회 (정규화: 80점)
- 계산: (100×0.5) + (90×0.3) + (80×0.2) = **93점**

**커뮤니티 활성도:**
- Reddit 게시물: 10,000개 (정규화: 88점)
- Discord 멤버: 50,000명 (정규화: 85점)
- 최근 30일 증가율: 50% (정규화: 75점)
- 계산: (88×0.3) + (85×0.3) + (75×0.4) = **81.9점**

**통합 인기도 (기본 가중치):**
- (82.5×0.4) + (92×0.2) + (93×0.3) + (81.9×0.1) = **86.89점**
