# LLM 인기도 웹사이트 PRD (통합 마스터 버전)

## 1. Executive Summary (요약)

### 1.1 프로덕트 개요
LLM(Large Language Model)의 종류와 다차원 인기도 지표를 시각화하고 비교할 수 있는 웹 애플리케이션입니다. 개발자들이 다양한 LLM을 탐색하고, 객관적인 인기도 지표를 비교하며, 프로젝트에 적합한 LLM을 선택할 수 있도록 돕는 정보 플랫폼입니다.

### 1.2 핵심 가치 제안
- **중앙화된 LLM 정보**: 다양한 LLM의 정보를 한 곳에서 확인
- **다차원 인기도 지표**: 단일 지표가 아닌 4개 카테고리의 종합 평가
- **데이터 기반 의사결정**: 객관적인 데이터로 LLM 선택 지원
- **사용자 커스터마이징**: 개인화된 인기도 계산
- **실시간 트렌드**: 시간에 따른 인기도 변화를 시각화
- **비교 분석**: 여러 LLM을 동시에 비교하여 최적의 선택 도움

### 1.3 목표
- 개발자들이 LLM 선택 시 소요 시간 50% 단축
- 월간 활성 사용자 10,000명 달성 (6개월 내)
- 사용자 만족도 4.5/5.0 이상
- 데이터 정확성 95% 이상

### 1.4 주요 특징
- LLM 목록 및 상세 정보 제공
- 4차원 인기도 지표 (개발자 커뮤니티, 학술적 영향력, 실용적 채택도, 커뮤니티 활성도)
- LLM 비교 기능 (최대 5개)
- 고급 필터링 및 검색 기능
- Flutter 웹 기반 반응형 디자인
- 사용자 커스터마이징 인기도 계산

## 2. Problem Statement (문제 정의)

### 2.1 해결하려는 문제
현재 개발자들은 LLM을 선택할 때 다음과 같은 어려움을 겪고 있습니다:

1. **정보 분산**: LLM 정보가 여러 플랫폼에 분산되어 있어 종합적 파악이 어려움
2. **주관적 평가 부족**: 객관적인 데이터 없이 주관적인 리뷰에 의존
3. **비교의 어려움**: 여러 LLM을 동시에 비교하기 어려움
4. **인기도 측정의 복잡성**: 다양한 지표를 종합적으로 파악하기 어려움
5. **최신 정보 부족**: LLM 생태계가 빠르게 변화하는데 최신 정보를 얻기 어려움

### 2.2 타겟 사용자의 페인 포인트
- **시간 소모**: 여러 소스를 방문하며 정보를 수집하는데 시간이 많이 걸림
- **불확실성**: 어떤 LLM이 실제로 인기 있고 신뢰할 수 있는지 판단하기 어려움
- **비교 어려움**: 여러 LLM의 특징과 성능을 한눈에 비교하기 어려움
- **정보 부족**: 특정 LLM의 상세 정보나 최신 업데이트를 찾기 어려움

## 3. Solution Overview (솔루션 개요)

### 3.1 핵심 솔루션
통합된 웹 플랫폼을 통해 개발자들이 LLM 정보를 쉽게 탐색하고 비교할 수 있도록 합니다. 하이브리드 데이터 수집 전략으로 실시간성과 비용 효율성을 모두 확보합니다.

### 3.2 주요 기능
1. **LLM 목록 표시**: 카드/리스트 형태로 LLM 정보 표시
2. **4차원 인기도 지표**: 개발자/학술/실용/커뮤니티 관점의 종합 평가
3. **비교 기능**: 최대 5개 LLM을 선택하여 상세 비교
4. **필터/검색**: 다양한 조건으로 LLM 필터링 및 검색
5. **사용자 커스터마이징**: 인기도 가중치 조정 기능

### 3.3 차별화 포인트
- **다차원 인기도 지표**: 단일 지표가 아닌 종합적인 인기도 평가
- **사용자 커스터마이징**: 가중치를 조정하여 개인화된 평가
- **실시간 트렌드**: 시간에 따른 인기도 변화를 시각화
- **하이브리드 데이터 전략**: 실시간성과 비용 효율성 균형
- **Flutter 웹**: 크로스 플랫폼 호환성과 성능

## 4. Target Users & User Journey (타겟 사용자 및 여정)

### 4.1 타겟 사용자

#### 페르소나 1: 김개발 (주니어 개발자)
- **나이**: 25-30세, **역할**: 풀스택 개발자
- **특징**: 챗봇 프로젝트를 시작하는 개발자
- **목표**: 프로젝트에 적합한 LLM을 빠르게 찾고 싶음
- **사용 패턴**: 인기도순 정렬 → 필터 적용 → 상세 비교

#### 페르소나 2: 박아키텍트 (시니어 개발자)
- **나이**: 30-40세, **역할**: 기술 리더
- **특징**: 여러 LLM을 평가하고 비교해야 하는 상황
- **목표**: 객관적인 데이터로 팀에 추천할 LLM 선택
- **사용 패턴**: 고급 필터 → 다중 비교 → 커스터마이징 가중치

#### 페르소나 3: 이연구 (연구자)
- **나이**: 25-35세, **역할**: AI/ML 연구자
- **특징**: 최신 LLM 트렌드를 파악하고 싶은 연구자
- **목표**: 학술적 영향력과 실용적 채택도를 함께 확인
- **사용 패턴**: 학술 인기도 중심 정렬 → 트렌드 분석

### 4.2 사용자 여정

#### 여정 1: LLM 탐색
1. **인지**: "프로젝트에 LLM이 필요한데 어떤 걸 써야 하지?"
2. **방문**: 웹사이트 접속
3. **탐색**: LLM 목록을 스크롤하며 둘러봄
4. **필터링**: 용도별 필터 적용
5. **상세 확인**: 관심 있는 LLM의 상세 정보 확인
6. **의사결정**: 인기도와 특징을 보고 선택

#### 여정 2: LLM 비교
1. **인지**: "여러 LLM 중에서 선택해야 해"
2. **방문**: 웹사이트 접속
3. **선택**: 비교하고 싶은 LLM 선택 (최대 5개)
4. **비교**: 지표와 특징을 나란히 비교
5. **커스터마이징**: 개인 우선순위에 맞게 가중치 조정
6. **의사결정**: 비교 결과를 바탕으로 최종 선택

## 5. Features & Requirements (기능 및 요구사항)

### 5.1 핵심 기능

#### 5.1.1 LLM 목록 표시
- **기능 설명**: 메인 페이지에서 LLM 목록을 카드 형태로 표시
- **표시 정보**:
  - 모델 이름, 개발사, 출시일
  - 4차원 인기도 점수 및 트렌드
  - 주요 특징 태그
  - 썸네일 이미지
- **우선순위**: Must Have
- **수용 기준**: 카드 표시, 정렬/필터링 정상 작동, 반응형 디자인

#### 5.1.2 4차원 인기도 지표 시스템
- **기능 설명**: 4개 카테고리의 인기도를 측정하고 시각화

**A. 개발자 커뮤니티 인기도 (Developer Community Popularity)**
- 측정 지표: GitHub Stars (40%), Forks (20%), Issues/PR (20%), Stack Overflow (20%)
- 데이터 소스: GitHub API, Stack Overflow API
- 업데이트 주기: 일일

**B. 학술적 영향력 (Academic Influence)**
- 측정 지표: 논문 인용 수 (60%), 관련 논문 수 (20%), 최근 증가율 (20%)
- 데이터 소스: Google Scholar, Semantic Scholar API
- 업데이트 주기: 주간

**C. 실용적 채택도 (Practical Adoption)**
- 측정 지표: Hugging Face 다운로드 (50%), PyPI 다운로드 (30%), Docker Pulls (20%)
- 데이터 소스: Hugging Face API, PyPI API, Docker Hub API
- 업데이트 주기: 일일

**D. 커뮤니티 활성도 (Community Activity)**
- 측정 지표: Reddit 언급 (30%), Discord 멤버 (30%), 30일 증가율 (40%)
- 데이터 소스: Reddit API, Discord API
- 업데이트 주기: 주간

**통합 인기도 계산**:
```
통합 점수 = (개발자×W1) + (학술×W2) + (실용×W3) + (커뮤니티×W4)
기본 가중치: W1=0.4, W2=0.2, W3=0.3, W4=0.1
```

- **시각화**: 레이더 차트, 라인 차트 (6개월 트렌드), 바 차트
- **우선순위**: Must Have

#### 5.1.3 사용자 커스터마이징
- **기능 설명**: 사용자가 인기도 가중치를 조정하여 개인화된 평가
- **프리셋**: 개발자 중심, 연구자 중심, 실용 중심
- **저장**: 로컬 스토리지에 설정 저장
- **우선순위**: Should Have

#### 5.1.4 비교 기능
- **기능 설명**: 최대 5개 LLM을 선택하여 나란히 비교
- **비교 항목**: 모든 인기도 지표, 기술 사양, 라이선스 정보
- **시각화**: 비교 테이블, 바 차트
- **내보내기**: CSV, 이미지 공유
- **우선순위**: Must Have

#### 5.1.5 검색 및 필터링
- **검색**: 이름, 설명, 개발사로 실시간 검색
- **필터**: 라이선스, 모델 크기, 용도, 출시 연도, 인기도 범위
- **정렬**: 각 인기도 기준, 이름, 출시일
- **우선순위**: Must Have

## 6. Technical Stack & Architecture (기술 스택 및 아키텍처)

### 6.1 기술 스택

#### 프론트엔드
- **프레임워크**: Flutter Web (현재 프로젝트 기반)
- **언어**: Dart
- **상태 관리**: Provider 또는 Riverpod
- **차트 라이브러리**: fl_chart
- **HTTP 클라이언트**: Dio
- **로컬 스토리지**: SharedPreferences, Hive

#### 데이터 수집 (하이브리드 전략)
- **실시간 데이터**: GitHub Actions + Python 스크립트
- **API**: GitHub, Hugging Face, Google Scholar, Reddit API
- **캐싱**: 로컬 스토리지 + 메모리 캐싱
- **데이터 저장**: JSON 파일 (GitHub Repository)

#### 호스팅
- **플랫폼**: GitHub Pages (무료) 또는 Vercel/Netlify
- **CDN**: 자동 제공
- **비용**: 월 $0-10

    ┌────▼────┐

## 8. Data Collection & Processing (데이터 수집 및 처리)

### 8.1 데이터 수집 전략 (하이브리드)
- **실시간 API 연동**: GitHub, Hugging Face (일일 업데이트)
- **주기적 수집**: 학술 데이터, 커뮤니티 데이터 (주간 업데이트)
- **수동 입력**: 초기 데이터 구축
- **커뮤니티 기여**: 사용자 제보 시스템

### 8.2 데이터 정규화 및 계산

#### 정규화 공식
```
정규화 점수 = (실제 값 - 최소값) / (최대값 - 최소값) × 100
```

#### 이상치 처리
- 상위/하위 1% 데이터는 계산에서 제외
- API 오류 시 마지막 성공 데이터 사용
- 데이터 부족 시 해당 카테고리는 계산 제외

### 8.3 데이터 검증 및 품질 관리
- **정확성 검증**: API 응답 유효성 검사
- **일관성 검사**: 데이터 형식이 표준 준수
- **완전성 검사**: 필수 필드 존재 확인
- **신선도 검사**: 업데이트 주기 준수 확인
